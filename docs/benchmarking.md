# Benchmark implementation and component workflows

See the root README for the complete paper suite. Commands below describe
individual experiment configurations; paths are relative to the repository root.
Use `--name native` / `--image-name native` for a separately published native image.


For a self-contained Linux ARM64 workflow (including data generation, downloads,
resume, and export), use [`bench`](../bench) and the [container instructions](#container-suite-local-and-graviton).

Usage:

```bash
python3 run_benchmarks.py --config example_experiment.json
python3 analyze_results.py --experiment-root out/experiments/example-local-validation
```

Everything generated by a run is written under `out/`.

- `run_benchmarks.py`: supported benchmark entry point
- `analyze_results.py`: post-run analysis and chart generation
- `benchmarking/`: runner, workload preparation, and analysis code
- `external_benchmarks/`: benchmark definitions, queries, and workload-specific helpers
- `paper/`: paper configs and figure scripts
- `duckdb/`: DuckDB/Prefix Range Filter prototype

## Comparing PRF implementations

`benchmarking/compare_prf_candidates.py` compares saved DuckDB shared libraries
against the already prepared native workloads in `out/experiments/paper-local`.
Keep a copy of the baseline library before rebuilding a candidate, then run:

```bash
python3 benchmarking/compare_prf_candidates.py \
  --baseline out/prf-baseline.dylib \
  --candidate tuned=duckdb/build/paper-native-release/src/libduckdb.dylib \
  --workloads job tpch jpb string ssb --repetitions 9 --profiles \
  --output out/analysis/prf-comparison.json
python3 benchmarking/summarize_prf_comparison.py out/analysis/prf-comparison.json
```

Linux builds can use `.so` libraries. Each library runs in a separate persistent
process with eight threads by default. Both compression modes are measured for
each library, in shuffled order within every repetition. Two warmups precede the
timed C API calls, which include planning and execution. Databases are opened
read-only. Result verification and optional profiles run outside the timed calls;
verification compares result multisets, allows rounding differences in floating
point aggregates, and substitutes `COUNT(*)` for nondeterministic `ANY_VALUE`
queries. `--queries` selects a smaller exploratory set and `--seed` changes the
measurement order.

The output records raw samples, medians, result checks, library checksums and
optional profiles. The summary produces per-query CSV and sums of query medians,
with paired bootstrap intervals for timing variation within that run. Uncompressed
controls help identify differences between worker processes; the intervals do
not account for systematic differences between machines or process placement.

The current PRF compression policy retains the 16 KiB cache target and limits
the cumulative increase in values covered by a bitmap to 6.25%. Direct-range
conversions retain the existing FPR limit. Builds of at most 4,096 rows with
bitmaps of at least 32 KiB use sparse bucket IDs during compression. Homogeneous
blocks are processed together, and an exact occupancy preflight can reject an
unprofitable first reduction before scratch allocation.

## Paper Filter Microbenchmarks

The main paper config also runs DuckDB's `filter_benchmark` and `range_benchmark`
from the same build as `duckdb-paper`. Activate the project's Python environment
with the packages in `requirements.txt`, then run:

```bash
python3 paper/run_paper_experiments.py --config paper/configs/local_paper_experiments.json
```

The optional top-level `microbenchmarks` object selects `system_name`, shared
`domain_size`, `total_keys`, `min_clusters`, `max_clusters`, `repetitions`, `seed`,
`construction_seed`, `grafite_bpk`, `diva_bpk`, and `max_fpr`, plus `probe_count` for points and
`queries_per_cluster_count` for ranges. Cluster bounds must be powers of two.
`aggregate` accepts `median` or `mean`. Each executable runs its filters internally;
SQL variants and SQL thread settings do not multiply or configure these measurements.

The publication config requires Bloom, Grafite, Diva, and both PRF modes. Diva
supports Linux x86-64 and ARM64; Grafite supports x86-64 and ARM64. Missing required filters fail the
run before measurements. This smaller config runs on the local platform and
records unavailable competitors:

```bash
python3 paper/run_paper_experiments.py --config paper/configs/local_paper_microbenchmarks_smoke.json
```

To rerun just these measurements or regenerate all figures from saved data:

```bash
python3 paper/run_paper_experiments.py --config paper/configs/local_paper_experiments.json --only-microbenchmarks
python3 paper/run_paper_experiments.py --config paper/configs/local_paper_experiments.json --skip-benchmarks
```

`--only-microbenchmarks` replaces the microbenchmark artifacts while preserving
SQL results, profiles, workload data, and the SQL summary, even when
`overwrite_output` is true. Changes to the saved SQL configuration require a new
experiment name. `--skip-benchmarks` needs neither a build nor benchmark execution;
it validates the saved manifest and CSV checksums. `run_benchmarks.py` also supports
`--only-microbenchmarks`, without figure generation. Binary systems must provide
both tools beside the selected CLI or in its `tools/` directory.

Under `out/experiments/<experiment>/`, the run writes:

- `microbenchmarks/filter-probes/{point,range}.csv`: raw measurements, including
  repetitions, seeds, measured FPR/counts, and range query kinds.
- `microbenchmarks/filter-probes/{point,range}.log` and `manifest.json`: commands,
  status, parameters, available filters, executable checksums, source/build and
  host metadata, and validation results. Failed/incomplete runs cannot be plotted.
- `paper/figures/filter_benchmark_overview.pdf`: point throughput, **range
  throughput**, summary size, build time, and point FPR, in that order.
- `paper/filter_benchmark_series.csv` and `paper/filter_benchmark_summary.{json,md}`:
  aggregated measurements, sample counts, and summaries, also registered in
  `paper/summary.{json,md}`.

The range comparison uses `range_query_kind: "empty"`, which all range-capable
filters measure. PRF's full and mixed ranges remain separate in the artifacts;
Bloom has no range curve. FPR comes directly from measured CSV values. Legacy
point exports with `actual_fpr` still work with `paper/figures/filter_benchmark.py
--csv ... --range-csv ...`; missing negative counts remain unknown. The standalone
range-latency script also selects empty ranges explicitly.

Focused pipeline checks:

```bash
python3 -m unittest discover -s tests -p test_microbenchmarks.py
```

All three microbenchmarks supply **sorted distinct build keys** to every summary.
Ordered/uniform labels describe the **probe stream**, not the build input.
Input generation, sorting, deduplication and shared validation are untimed;
summary-specific hashing, sorting, allocation and encoding are construction work.
Point probes produce selection vectors for all implementations; membership-oracle
checks run outside the timers. PRF allocation and Bloom hash-buffer construction
are included in build time, and the measured Bloom instance is reused for probing.
Diva already consumes sorted keys. Grafite's hashed output is checked for a sorted
run or a cyclic rotation; other hashed outputs are sorted normally.

Grafite no longer silently clamps the requested budget. It uses approximate
Grafite at that budget when the reduced universe is smaller than the input
universe; otherwise it stores exact Elias–Fano using the same SUX backend.
This is an explicit **Grafite + exact fallback** comparison. The adapter records
`adapter_representation`, `requested_bpk`, hash parameters and reduced universe;
actual `summary_bytes` and measured FPR remain the basis for comparison. Requested
bits per key are a model parameter, not a hard cap on storage including metadata.
Range queries crossing hash blocks are split safely; intervals covering a whole
reduced universe conservatively pass. Exact mode has zero false positives.

Both randomized adapters use a per-construction seed derived from
`construction_seed` (default 42), the sorted build checksum and the zero-based
measured repetition. Equal build sets get equal seeds across tools and probe
layouts. Warmups and execution order do not affect measured constructions.
Changing the base seed gives an independent reproducible series. Runtime still
varies with scheduling and caches; deterministic seeds reproduce the filter and
its answers, not identical elapsed nanoseconds.

The corresponding DuckDB branch is `d-justen/duckdb:prf-v2`. Commit
`087b4fb9d9` publishes the previously local PRF optimizations; commit
`4895e6f2c080601422e5c70882a1ab934600b3f4` adds the adapters and timing contract.
Commit `0b737d677c9730fb8e48b8e89ed303f782f6bc73` adds bounded interval compression
for serial and parallel PRFs, with the same final bitmap/direct-range layout.
It includes Diva ARM64/SVE2 support (`72dd6b6893`) and deterministic single-case
benchmark execution (`61316348b3`). The compression setting and benchmark result
schemas remain compatible. See [the compression validation guide](../duckdb/tools/PRF_COMPRESSION.md)
for exact-representation tests and separate first-pass/warmed probe measurements.
For a clean existing DuckDB checkout, update and rebuild before rerunning:

```bash
git -C duckdb switch prf-v2
git -C duckdb pull --ff-only origin prf-v2
# Use checkout 0b737d677c9730fb8e48b8e89ed303f782f6bc73 instead to pin this implementation.
venv/bin/python paper/run_paper_experiments.py --config paper/configs/local_paper_experiments.json --only-microbenchmarks
```

The git-system runner rebuilds the tools from the selected source. A full SQL
rerun is also needed to replace the old intro/string-join/JPB PRF measurements;
`--only-microbenchmarks` intentionally preserves those historical SQL results.

Version-2 manifests record this contract, source content hashes (including
untracked source), binary hashes, and build settings. Version-1 measurements must
be rerun to claim corrected Grafite behavior; replotting does not repair them.
The adapter-only target can validate both competitors on Linux x86-64:

```bash
cmake --build duckdb/build/release --target range_filter_adapter_tests -j 4
duckdb/build/release/tools/range_filter_adapter_tests
```

## Simulated JPB Filter Execution

The native paper config also runs `join_pruning_benchmark` and produces
`paper/figures/jpb_simulated_filtering.pdf` (with a PNG preview). The four panels
separate ordered/uniform probes and small/large dimensions. Each query has one
bar per available filter, showing **total execution time** (build + range + point).
Build includes allocation, insertion, analysis/compression, and finalization.
Bar heights are arithmetic means of repetition totals; error bars show one
sample standard deviation of those totals. Panels share a logarithmic y-axis by
default. `--jpb-y-scale linear` on either `paper/run_paper_experiments.py` or
`python -m paper.figures.build_all` selects a shared linear axis starting at zero.
Phase timings remain in the raw CSV, aggregated CSV, and JSON exports. On log axes,
error bars crossing the lower display limit are clipped and disclosed in the caption.
Zero total times require the linear option.

The optional `jpb_microbenchmarks` configuration selects `system_name` and
`workload_name`, plus `repetitions`, `warmups`, `order_seed`, `construction_seed`, `grafite_bpk`,
`diva_bpk`, `max_fpr`, and `required_filters`. The workload reference supplies the
query definitions, seed, cardinalities, selectivity, and row-group size. The
first version supports native dimension-cardinality sweeps with one join,
distinct dense positive integer keys, and at least two selected build keys.
Both PRF modes are always required; the publication config also requires
Grafite and Diva. Missing required implementations fail before the JPB replay.

This measures **simulated filtering time**, not SQL query latency. Selection SQL
from the existing JPB generator prepares sorted build keys outside the timers.
Probe keys and logical row-group min/max metadata are also prepared outside the
timers. Ordered keys use `1 + floor(row_index * domain_size / probe_rows)`;
uniform keys use a fixed `mt19937_64` sequence modulo the domain. Uniform inputs
match JPB's distribution, not an existing database's exact random sequence.
Input data stays fixed across repetitions; filter order is shuffled and construction
seeds vary reproducibly by build-key checksum and measured repetition.
One probe column is reused across predicates, requiring about 4 GB at the
500-million-row paper scale, plus validation/output bitmaps and filter storage.

Every repetition builds a fresh filter. Empty groups are skipped; PRF's
always-passing groups bypass point filtering; the remaining rows receive
2048-row point-probe batches. All implementations produce selection vectors and
write selected rows into a common output bitmap within the point timer. Scratch
allocation and correctness checks are untimed. The simulation is single-threaded
and does not include storage decoding, I/O, hash-table probes, aggregation,
column-segment pruning, or automatic PRF-to-Bloom fallback. It records actual
candidate rows and false positives, including always-passing groups, to expose
work that would remain for a real join. Range false positives use truly empty
key intervals as their denominator; overall false positives use nonmatching
probe rows. Rates with no negative examples remain undefined. False negatives
fail the run.

From the repository root, with the native CMake build configured:

```bash
CCACHE_DISABLE=1 cmake --build duckdb/build/paper-native-release --target duckdb join_pruning_benchmark -j 4
venv/bin/python paper/run_paper_experiments.py --config paper/configs/local_paper_jpb_microbenchmarks_smoke.json --only-microbenchmarks
venv/bin/python paper/run_paper_experiments.py --config paper/configs/local_paper_jpb_microbenchmarks_smoke.json --skip-benchmarks
venv/bin/python -m unittest discover -s tests -p test_jpb_microbenchmarks.py
```

The smoke config requires only PRF and explicitly reports unavailable competitors.
Its binary path is relative to the working directory, following existing binary
system configuration conventions. The main `local_paper_experiments.json` runs
this suite alongside the primitive filter microbenchmarks and SQL experiments.
`--only-microbenchmarks` runs whichever microbenchmark suites are configured while
preserving SQL results and workload files. `--skip-benchmarks` needs no compiler
or competitor libraries.

Raw timings, counts, representation/memory information, input fingerprints,
selection SQL, the run log, and a checksummed manifest live in
`microbenchmarks/jpb-simulation/`. Plot data and the caption are saved as
`paper/jpb_simulated_filtering_series.csv` and
`paper/jpb_simulated_filtering_summary.json`, and registered in the paper summary.
The manifest validates both referenced workload definitions and saved artifacts.
Tests use real available implementations, plus synthetic four-filter plotting
fixtures. Grafite supports x86-64 and ARM64; Diva supports Linux x86-64 and ARM64.
A PRF-only smoke run does not validate competitors.

## Generated Join-Pruning Sweeps

New `cross_product` workloads use one explicit sweep and a set of fixed
parameters. Compatible sweeps can also select an explicit query suite:

```json
{
  "kind": "cross_product",
  "params": {
    "fixed": {
      "fact_rows": 100000000,
      "dimension_cardinality": 1000000,
      "key_domain_size": "dimension_cardinality",
      "selectivity": 0.01,
      "join_count": 1,
      "build_key_multiplicity": 1,
      "probe_layout": "uniform",
      "row_group_size": 122880,
      "seed": 7
    },
    "sweep": {
      "kind": "dimension_cardinality",
      "values": [100000, 10000000]
    },
    "query_types": [
      {"kind": "range", "probe_layouts": ["ordered", "uniform"]},
      {"kind": "shoulder", "probe_layouts": ["ordered", "uniform"]},
      {"kind": "seasonal", "cluster_count": 10, "probe_layouts": ["ordered", "uniform"]},
      {"kind": "scattered", "probe_layouts": ["ordered", "uniform"]}
    ]
  }
}
```

Supported sweeps are `dimension_cardinality`, `selectivity`,
`key_domain_size`, `build_key_multiplicity`, `join_count`, `cluster_count`,
and `row_group_size`. A cluster-count sweep defines its query layout and does
not accept `query_types`; cluster counts start at two. Join-count sweeps use
distinct dimension keys and independent uniform fact keys. Multiplicity
sweeps keep total dimension cardinality fixed. The default density mode draws
fact keys only from keys present in the dimension. Row-group sweeps create native
DuckDB fact databases, leaving dimension storage fixed.

`key_domain_size` accepts an integer, `"dimension_cardinality"`, or
`"dimension_distinct_keys"`. The last form is useful for multiplicity sweeps:
it keeps the domain dense while the fixed number of dimension rows is divided
among progressively fewer distinct keys.

Every new-style prepared workload materializes its contract in `definition.json`, its
resolved sweep points in `cases.json`, and per-query parameters in
`queries/query_catalog.json`. These files are the authoritative experiment
description; filenames are only human-readable labels. Legacy cross-product
configurations remain accepted for existing experiments.

The six paper parameter sweeps live in
`paper/configs/local_paper_sweeps.json`. They produce a shared 2x3 runtime
figure with one panel each for join count, build-key multiplicity,
selectivity, density, cluster count, and row-group size:

```bash
python3 paper/run_paper_experiments.py \
  --config paper/configs/local_paper_sweeps.json
```

The standardized sweep writes to `out/experiments/paper-sweeps-standardized-local`
and refuses to overwrite an existing run. Its common baseline is 500 million fact
rows, 100 million dimension rows and key-domain size, 1% selected keys, one join,
one row per key, uniform probes, 122,880 rows per group, and seed 7. All variants
disable `compressed_materialization`; the run uses eight threads and ten repeats.
The one-join, one-row-per-key, 1% selectivity, 100-million density-domain, and
default-row-group points share the same logical keys, payloads, and FK mapping.
The two-cluster point has the shoulder selection. Physical table widths and
storage layouts can still differ between sweeps.

For multiplicity, both the 100-million total dimension rows and whole key domain
stay fixed. Scattered keys spread over the domain as their count decreases.
Shoulder keys form two contiguous ranges anchored at the domain boundaries;
their widths shrink with multiplicity. Separate dimension layouts and fact FK
columns prevent the shoulder layout from changing scattered key spacing.

The density sweep uses `"cardinality_mode": "fixed_selected_build_and_probe"`.
It fixes the **selected** build side at one million unique keys while varying
the domain through 5M, 10M, 30M, 100M, 300M, and 1B. The unfiltered dimension has
one row per domain key, so its predicate selectivity is `1M / domain size`.
Each domain and query shape has its own fact FK column. Every fact row retains
its matching/nonmatching status from the 100M baseline; it samples uniformly
within the corresponding selected set or complement. Consequently, output
cardinality stays exactly constant across domains **within each query shape**.
The number is the realized baseline count (approximately five million), not a
newly rounded target. Away from 100M these probes are conditionally uniform,
not uniform over the whole numeric domain. At 100M the original FK values are
reused exactly. This mode currently requires one join, unique build keys,
shoulder/scattered uniform queries, and default native DuckDB row groups.

Density fact generation uses consecutive batches of 983,040 rows (eight native
row groups), bounding the ASOF lookup and order-restoration sorts. It preserves
the FK values, matching rows, and physical fact-row order. The density workload's
`params.preparation` config sets `batch_rows`, `threads`, `memory_limit`,
`max_temp_directory_size`, and optionally `temp_directory` (absolute or relative
to the workload artifact directory). Batch size must be a positive multiple of
122,880. The paper config uses four preparation threads, 8 GiB memory, and a
64 GiB spill limit; benchmark execution still uses eight threads. These limits
apply to density preparation, including dimension generation.

To continue a run that failed during preparation, keep its output directory and run:

```bash
python3 paper/run_paper_experiments.py \
  --config paper/configs/local_paper_sweeps.json \
  --resume-preparation
```

This reuses completed workload manifests and density dimensions, including
dimensions saved by the earlier generator before its fact-table creation failed.
Fact batches and their restart position commit together, so later failures resume
from the last committed batch. Incomplete workloads other than density restart
their preparation. Resume requires the saved experiment configuration to match;
preparation resources and `overwrite_output` may change. It is only supported
before benchmarking has started. After preparation finishes, benchmarking and
figure generation proceed normally.

`query_catalog.json` distinguishes dimension predicate selectivity, probe
selectivity, selected build cardinality, key density, reference domain, and
expected output cardinality. Figure summaries retain these parameters for each
point. For the density panel, the caption should state: “One million selected
unique build keys; matching fact rows fixed to the 100M-domain baseline per query
shape; conditional uniform FK distribution.” For multiplicity: “100M total
dimension rows and whole key domain; contiguous boundary shoulders or scattered
keys with increasing spacing.” Existing results use their original contracts
and should not be mixed with the standardized run.

The paper configuration also includes the local `dynamic-predicate-transfer/`
checkout as the `rpt-plus` system. Its three variants select `rpt_filter=none`,
`cascade`, and `prf`; the PRF variant explicitly enables
`rpt_prf_scan_pushdown`. The RPT+ system currently runs the Join Pruning, JOB,
TPC-H Skew, and SSB Ordered workloads. String joins and DuckLake are excluded.

The vendored regular PRF is the reference implementation. RPT+/PRF uses its fixed
bitmap sizing, source-statistics multiplicity estimate, 0.1% false-positive
budget, at-most-four direct ranges, and 16 KiB compression cache target. It also
uses the same sector Bloom construction as the fallback when the initial PRF
estimate exceeds the budget. Both engines' JSON profiles expose representation,
FPR, fallback choice, and compression time. RPT+ additionally reports build rows,
estimated multiplicity/distinct keys, shifts, and transfer direction. The two engines still
differ in version, propagation direction, scheduling, and probe batch handling.
Their source distinct-count estimates can differ when they materialize data
separately. The parity check tests compression with identical supplied statistics
and executes SQL against a single shared database, including its persisted
statistics. The SQL fixtures mix selected and rejected rows to avoid RPT's early
selectivity-sampling cutoff.
Source identity is intentionally omitted from experiment metadata.

Focused validation (without generating or running the paper sweep):

The parity script compiles a small fixture against each built library using `c++`
(or `--cxx`) and runs both explicit-statistics and SQL checks at one and four threads.

```bash
python3 -m unittest discover -s tests -p test_cross_product_sweeps.py
dynamic-predicate-transfer/build/paper-native-release/test/unittest '[rpt_prf]'
python3 paper/validate_prf_parity.py --prf duckdb/build/paper-native-release/duckdb \
  --rpt dynamic-predicate-transfer/build/paper-native-release/duckdb
```

## Filter Build Profiling

Standard JSON profiling records comparable elapsed timings in each hash join's
`join_filter` object. The benchmark imports them into `profile_runs` and reports
them for compressed PRF, uncompressed PRF, Bloom-only, and disabled-filter variants:

| Result field (milliseconds) | DuckDB profile field (seconds) | Meaning |
|---|---|---|
| `join_finalize_build_ms` | `join_finalize_build_elapsed_seconds` | Hash-table finalization and filter construction, excluding PRF postprocessing |
| `prf_analysis_ms` | `prf_analysis_elapsed_seconds` | Standalone PRF analysis, including the uncompressed fallback decision |
| `prf_compression_ms` | `prf_compression_elapsed_seconds` | PRF compression, including its bitmap analysis |
| `join_finalize_ms` | `join_finalize_elapsed_seconds` | Total of the three phases above |

The build column is labeled **Join/filter build** because it includes hash-table
work. It is not an isolated PRF or Bloom construction cost. A PRF followed by Bloom
fallback counts as one elapsed build interval; `prf_build_count` and
`bloom_build_count` both increase. Bloom-only runs have zero PRF analysis and
compression; uncompressed PRF can have nonzero analysis but zero compression.
Finalization, perfect-hash, and external-finalization counts are retained too.

`paper/run_paper_experiments.py` and `paper/figures/build_all.py` write
`paper/filter_phases.csv` for every query and variant, including all sweep points.
The paper summary table has separate build, analysis, and compression columns;
DuckLake JPB runtime figures annotate the three phases; native JPB figures show
only total runtime and scanned tuples. `analyze_results.py` includes
per-query `filter_phases` in each workload/system's `analysis/summary.json` entry.
Existing result databases acquire the new columns when metrics are imported.

These timings come from one separate profiled execution, while runtime bars use
repetition medians. Spans from concurrent joins can overlap and must not be
interpreted as an additive decomposition of query latency. External joins report
initial finalization only. Worker timings are not substituted for elapsed time.
Old `prefix_range_filter.build_phase_elapsed_seconds` and
`compression_phase_elapsed_seconds` have different boundaries; older profiles,
including RPT+ profiles without `join_filter`, therefore show blank CSV cells or
dashes for the new timings. Explicit zero remains zero. Missing phases cannot be
recovered from old timings; a fresh profile is needed.

The profiling pipeline selects `profiling_mode='standard'`, which provides these
elapsed metrics without detailed worker/probe instrumentation. Focused parser,
reporting, migration, and small engine checks can be run with:

```bash
python3 -m unittest discover -s tests -p test_filter_profiles.py
```

Git systems may set `checkout_dir` to use a source tree other than the shared
`duckdb/` checkout. Systems may set `workload_names` to run only a subset of the
configured workloads. Paper figure generation combines systems when
`--system-name` is omitted, so variant labels must be unique across those
systems.

### TPC-H Skew

Expected file: `external_benchmarks/tpch-skew/tpch_sf100_z2.duckdb`

`TPCDSkew/` contains Microsoft's
[Program for TPC-H Data Generation with Skew](https://www.microsoft.com/en-us/download/details.aspx?id=52430),
the tool cited in reference 29 of
[Pushing Data-Induced Predicates Through Joins](https://www.vldb.org/pvldb/vol13/p252-orr.pdf).
The name means **TPC-D + skew**, not TPC-DS: it generates the eight TPC-H tables.
The source identifies itself as TPC-D DBGEN 1.3.1 with the Chaudhuri/Narasayya
skew extension. `-z 0` selects uniform data and `-z 2` selects Zipf skew 2.
This is the historical research generator, not the current official TPC-H tool.

Build on macOS or Linux with a C compiler and CMake (from the repository root):

```bash
cmake -S TPCDSkew -B out/tpcdskew-build -DCMAKE_BUILD_TYPE=Release
cmake --build out/tpcdskew-build --parallel 2
mkdir -p out/datasets/tpch-sf001-z2
DSS_CONFIG="$PWD/out/tpcdskew-build" \
  DSS_PATH="$PWD/out/datasets/tpch-sf001-z2" \
  out/tpcdskew-build/dbgen -s 0.01 -z 2
```

The separate build directory avoids reusing the object files and macOS executable
bundled with the supplied source. The build supports LP64 macOS/Linux, including
ARM64. The portability fixes use the system `getopt`, define the skew row counter
on Linux, and correct output-file handling; they retain the existing generator
and BCD key algorithm. Only `dbgen` is built; experiments use this repository's
SQL queries instead of the legacy `qgen`.

Alternatively, build and run the standalone generator container:

```bash
docker build --platform linux/arm64 -t join-pruning-tpcdskew TPCDSkew
mkdir -p out/datasets/tpch-docker-sf001-z2
docker run --rm --platform linux/arm64 \
  --user "$(id -u):$(id -g)" \
  -v "$PWD/out/datasets/tpch-docker-sf001-z2:/data" \
  join-pruning-tpcdskew -s 0.01 -z 2
```

This container only generates `.tbl` files; it does not run experiments or manage
EC2. Use a fresh output directory, or pass `-f` to explicitly overwrite files.
For the paper dataset, replace `-s 0.01` with `-s 100`. Use serial generation;
the legacy parallel/partitioned skew-generation paths have not been validated.
The smoke checks cover SF 0.01, not a fresh full SF 100 generation.

To materialize a database, execute `external_benchmarks/tpch-skew/schema.sql`

## Container suite: local and Graviton

Stages 1–5 are implemented by `bench` and `benchmarking/suite.py`. This workflow
builds both DuckDB forks, all three filter microbenchmark executables, the patched
TPC-D/Skew generator, and a pinned SSB generator into one Linux ARM64 image.
It runs on an ARM Mac through Docker Desktop or on a Graviton Linux host.
EC2 provisioning, S3 delivery, cross-instance resume, and shutdown are provided
by `bench ec2`; see [AWS execution](#aws-execution) below. The `build` and `local`
commands do not create cloud resources.

The host needs Docker with Buildx and Python 3.12 or newer. Python benchmark and
plotting dependencies are installed inside the image. Start with:

```bash
./bench build
./bench local all --config configs/smoke.json --run-id smoke-01
```

The build uses the checked-out PRF and RPT+ source trees, including local changes.
It archives SSB commit `361661aebb4ab21fc6742805e42791a0012a13db` from
`../ssb-dbgen` when available, otherwise clones its public repository.
`--ssb-source /path/to/ssb-dbgen` selects another checkout containing that commit;
uncommitted sibling changes are deliberately excluded. `--jobs` controls build
parallelism (default 2). DuckDB native CPU tuning is disabled. Diva, Grafite, Bloom,
and PRF are included. Diva uses portable ARM code locally and a separate SVE2
bit-permutation executable when Linux reports the required CPU features. Only
Diva is compiled with SVE options; PRF, Grafite and the drivers retain their
compilation settings. The image builds both versions and runs portable adapter
and bit-operation tests. Graviton runs repeat those tests on the selected backend. Source hashes, commits, binary hashes, image ID, input
checksums, configuration, and host/cgroup information accompany the results.
The base image and Python package versions are pinned; Ubuntu package updates
can change a rebuild, so retain the built image by digest for exact reuse.

`configs/smoke.json` exercises every data adapter, all configured PRF/RPT+
variants, both microbenchmark suites, profiles, analysis, and export. It uses
two CPUs, a 6-GiB container limit, and a 2-GiB DuckDB limit. Generated data is
small (TPC-H and SSB at SF 0.01); JOB uses the **complete** historical IMDB
snapshot with two queries. Its first preparation downloads about 1.8 GB, plus
OurAirports. Allow additional space for the loaded database and Docker builds.
This checks the workflow; laptop timings are not Graviton performance results.

Data and spill files default to Docker volume `join-pruning-data`. Durable
artifacts appear in `out/suite-results/smoke-01/`, with a sibling `.tar.gz` archive
and archive checksum. `--work /path` uses a bind mount instead of the volume;
`--results /path` changes the durable output directory. The launcher writes
results as the invoking host user. Without `--run-id`, it creates a unique ID.

### Stages and resume

```bash
# Resume this exact configuration/image; completed measurements are skipped.
./bench local all --run-id smoke-01 --resume

# Or keep preparation and measurement separate.
./bench local prepare --run-id prepared-01
./bench local run --run-id prepared-01 --resume
./bench local analyze --run-id prepared-01
./bench local export --run-id prepared-01
```

`prepare` validates or builds cached inputs without measuring. `run` requires
prepared data, runs SQL and microbenchmarks, and assembles the result database.
`analyze` rebuilds summaries, CSVs and plots from completed unit databases;
`export` packages the run. `all` performs these in order, preparing one workload,
running it across systems/variants, then evicting its managed data after success.
Shared external datasets are retained through their last dependent workload.
Failed workloads retain their inputs for retries. Downloads remain cached.
Standalone `prepare` retains all workloads and therefore needs more disk space.

With `suite.checkpoint_queries=true` (the native smoke and full defaults), the
checkpoint boundary is one **system/workload/variant/query**, retaining all
warmups and repetitions for that query. Otherwise it is the entire variant.
A failed or interrupted unit is retried in full. Each unit has its
own database; only successful, validated units enter the aggregate database.
Resume checks the configuration, runner source, image/runtime and binaries, and
verifies completed database and profile checksums. Changes require a new run ID. Concurrent access
to a run or shared cache is rejected. A timeout terminates the entire worker
process group. Later units continue after a unit failure; the command returns
nonzero, records partial status, and `all` still exports the available results.

`units/*/` contains attempts, logs, settings, completion state, and sampled
process-group RSS, disk I/O and spill high-water marks, plus worker/child peak
RSS and CPU usage from the OS. Group sampling is approximate, not a replacement
for hardware performance counters. SQL profiles and timings
remain separate, following the existing runner. Preparation also receives the
configured thread, memory and spill limits. JPB simulation remains intentionally
single threaded; its input SQL gets memory/spill limits, while its C++ vectors
are bounded by the container limit. Swap is disabled at the container boundary.

Downloads in `docker/datasets.lock.json` have fixed URLs, SHA-256 hashes and
sizes. Cache keys include generator binaries/distributions, schemas, preparation
code, versions and parameters. A completion marker is written only after loading,
row-count/key validation and checkpointing. Partial downloads/databases are
never accepted as complete. Original SSB keeps generator order; ordered SSB
sorts `lineorder` by date with original row order as the tie breaker. For SF < 1,
the SSB adapter separately generates the full fixed date dimension because the
upstream generator otherwise scales it down. Both variants use the repository's
SSB query set.

### Full configuration on an 8-vCPU host

`configs/graviton-full.json` preserves the paper's large JPB/string workloads,
JOB queries, skewed TPC-H SF 100/z=2, SSB SF 100, intro variants, all six paper
parameter sweeps and repetitions.
It adds original-order SSB alongside ordered SSB. It uses 8 threads, 20 GiB of
DuckDB memory, a 28-GiB container limit, and up to 120 GiB of spill. These defaults
target the planned 32-GiB host. A 16-GiB host needs smaller memory limits.
Datasets may exceed RAM; disk estimates and the free-space reserve are checked
before preparation, with a reserve guard during each worker.

On an already provisioned host, with NVMe mounted at `/mnt/benchmark` and durable


These paths must already be mounted and writable; the launcher does not format
devices. Peak-space estimates are conservative configuration inputs, not proof
that every scale fits. A resource failure remains visible in the run status.
The full configuration requires the sweep and microbenchmark figures.
`coverage.json` checks every configured SQL query, variant, repetition and profile;
missing workloads and required figures cause a nonzero exit. Microbenchmark
capabilities are checked before dataset generation and saved in `capabilities.json`. Smoke runs produce
a compact overview; their reduced dimensions are not the paper's experiment.

The archive contains results, profiles, query definitions, microbenchmark CSVs,
logs, metadata, plots and `SHA256SUMS`, excluding datasets, spill and binaries.
After extracting it elsewhere, analysis needs only the Python dependencies:


### Sweep jobs and Diva follow-up runs

`configs/graviton-sweeps.json` contains only the six paper sweeps: 53 parameter
values, 89 query cases, eight variants, ten repetitions and profiling. It produces
`paper/figures/parameter_sweep_overview.pdf`. `configs/graviton-microbenchmarks.json`
reruns the point/range benchmarks and JPB simulation with Diva required; it does
not generate the SQL datasets or repeat SQL workloads. Existing results remain
separate under their original run IDs.

Validate locally with the reduced configurations:

```bash
./bench build
./bench local all --config configs/smoke-microbenchmarks.json --run-id diva-smoke
./bench local all --config configs/smoke-sweeps.json --run-id sweeps-smoke
```

Diva backend selection happens before timing. `--diva-backend portable` forces the
portable executable; `--diva-backend sve2` requires SVE2/bitperm hardware and fails
on unsupported hosts. The default is `auto`. For EC2, the same override is
`suite.diva_backend` in the config. Selected executable paths, checksums and
backend names are recorded. The laptop's portable measurements do not establish
Graviton performance; compare both backends on the target hardware with matching
inputs. The port retains Diva's integer-optimized filter, original x86 BMI2 path,
load factor, bit budget and seeds. Its boundary-case correction handles the
otherwise empty bulk-load tail at 1024*k+1 keys.

`configs/graviton-diva-pilot.json` adds a sequential portable/SVE comparison on
one Graviton host, using one million build keys. It verifies identical build
inputs, space usage and answers, then records build-time and throughput ratios in
`diva-comparison/comparison.json`; the raw measurements are retained alongside it.
This diagnostic is enabled with `suite.compare_diva_backends`. On hosts lacking
SVE bit permutation it explicitly reports `unavailable`. It does not establish
performance equivalence with an x86 CPU. For a short EC2 validation:

```bash
./bench ec2 publish --image join-pruning-suite:local
./bench ec2 launch --config configs/graviton-diva-pilot.json \
  --instance-type m9gd.large --max-runtime-seconds 1200 --run-id diva-pilot-01
./bench ec2 fetch --run-id diva-pilot-01
./bench ec2 cleanup --run-id diva-pilot-01 --delete-volumes
```

Fetch after final delivery and cleanup after the instance stops, as with other
runs. The full-scale follow-up uses `configs/graviton-microbenchmarks.json`.

The large sweeps need substantial preparation: multiplicity stores 1.5 billion
dimension rows, density 1.445 billion, and the row-group sweep writes six
500-million-row fact databases. Disk estimates include spill allowance but need
confirmation with a preparation pilot. To give each sweep a separate 24-hour
attempt, split the configuration without changing any workload's parameters:

```bash
./bench split --config configs/graviton-sweeps.json --output out/sweep-jobs
./bench ec2 launch --config out/sweep-jobs/jpb-sweep-joins.json --run-id sweep-joins-01
# Launch the other five generated configs under distinct run IDs.
./bench ec2 fetch --run-id sweep-joins-01
# Fetch each completed job, then combine all six downloaded directories:
./bench combine --config configs/graviton-sweeps.json --run-id sweeps-combined \
  --runs out/ec2-results/sweep-joins-01 out/ec2-results/sweep-multiplicity-01 \
         out/ec2-results/sweep-selectivity-01 out/ec2-results/sweep-density-01 \
         out/ec2-results/sweep-clusters-01 out/ec2-results/sweep-row-groups-01
```

Each job is launched explicitly; splitting does not allocate instances. Combining
requires all six jobs, matching original configurations, runner/image/binary
identities and valid measurement checksums. It copies results into a new directory
and generates the shared figure with Docker. Combined results are for analysis
and export; resume the original job when measurements are incomplete. Concurrent
jobs need separate data caches when running locally.

Preparation settings can be supplied in `suite.preparation` or a workload's
`preparation` object. Density's existing `params.preparation` settings are also
honored. Thread/memory/spill settings are capped by the benchmark resource limits;
the runner always assigns the spill directory. Thus density retains its explicit
four-thread, 8-GiB preparation budget while measurements use eight threads.
Interrupted density generation resumes committed batches when the same cache is
available and the source/config identity matches. Failed or partial data is never
accepted as complete. EC2 stop loses local NVMe: dataset preparation is regenerated
on a replacement instance, while completed query measurements resume from S3.
Splitting reduces the work per attempt; it does not guarantee a large preparation
fits 24 hours. Retain the shutdown deadline and use the pilot to assess that limit.

### Ordered dimensions and DuckLake on S3

`configs/graviton-ordered-ducklake.json` is an alternative to `graviton-full.json`.
It keeps 500M fact rows and 1% selectivity, with ordered fact foreign keys only.
The native workload crosses 100K, 1M, 10M, 100M and 1B dimension cardinalities with
range, shoulder, seasonal_8, seasonal_16, seasonal_32 and scattered predicates.
These are unfiltered dimension sizes; at 1% selectivity their build sides contain
1K, 10K, 100K, 1M and 10M rows, respectively. Each dimension has unique keys
from 1 through its cardinality.
It retains the native variants and JPB filter simulation. The ordered figure
uses one panel per dimension cardinality; simulation results distinguish each
seasonal predicate.

`configs/graviton-ordered-1b.json` runs just the new 1B dimension on a separate
instance: six predicates, eight native variants, and the six matching filter
simulation cases. Use the original published image to keep the binaries comparable.
`bench combine --dimension-cases` accepts a single-workload SQL-only target config
and disjoint dimension partitions, including a completed native workload from a
run whose other workloads are still active. It validates software/hardware,
benchmark settings, checksums and full query coverage, preserves source evidence,
and creates an analysis-only combined result. Filter simulation artifacts remain
with their source runs until all desired simulation cases are available.

The second workload uses a 1M dimension and the same six predicates. Every
variant—no pre-filter, Bloom, Bloom + min/max and PRF with fallback—queries
DuckLake over the same immutable S3 objects. Four deterministic fact strings of
32 characters are generated independently from row ID, column number and seed;
the query consumes two with a checksum aggregate. Parquet exports use 122,880
rows per row group and eight groups per file, yielding about 509 fact files.
The additional columns and smaller files make avoided reads measurable.

The EC2 host uploads the Parquet files into a dedicated, unversioned scratch
bucket under `scratch/<run>/<attempt>/<workload>/`. Each worker registers those
files using `ducklake_add_data_files` in a local DuckLake metadata catalog.
Before measuring, it compares catalog key min/max, file sizes and row counts
with the local Parquet metadata. Range-query validation requires Bloom + min/max
and PRF to exclude fact objects before fetching their footers. No variant scans
Parquet directly. Catalog setup and upload are outside the timed queries.

The HTTPFS patch counts actual GET response-body bytes, including retries and
read-ahead. It records per-object bytes and attempted GET counts for each timed
repetition, separately summing fact bytes and total data bytes. Counters reset
after warmup, and external-file and HTTP metadata caches are disabled. The
`join_pruning_ordered_ducklake.pdf` figure mirrors runtime above fact bytes read
in GiB, with medians across repetitions. Bytes exclude headers, TLS overhead,
uploads and the local catalog; they are not inferred from scanned rows or file
sizes. Raw measurements are in `timing_runs`, and plotted values are also
exported as `paper/join_pruning_ordered_ducklake_series.json`.

The suite deletes its workload prefix on completion or failure; the host also
cleans the entire attempt prefix when the container exits or is stopped. Cleanup
lists the prefix again to verify it is empty and saves a report under `s3/`.
A two-day bucket lifecycle covers abrupt host loss. Resume regenerates and
uploads disposable data under a new attempt while preserving completed query
measurements. Results remain in the separate, versioned results bucket.

Checkpoint matching ignores the managed DuckLake S3 staging URL while still
checking the query, configuration and output checksums. For runs pinned to older
images, the resume host rebinds verified checkpoint scheduling metadata to the new
attempt URL before starting the original image. It preserves the original metadata
under `cloud/<attempt>/ducklake-resume/`; measurement files and the original S3
checkpoint remain unchanged. This repair ships with `bench ec2 resume`, so an
already-running experiment does not need its image replaced or measurements restarted.

Build/publish the **extensions** image and update the stack before launching:

```bash
./bench ec2 deploy
./bench build --target extensions --image join-pruning-suite:extensions
./bench ec2 publish --image join-pruning-suite:extensions --name extensions
./bench ec2 launch --image-name extensions --instance-type m9gd.xlarge \
  --config configs/smoke-ducklake-s3.json --max-runtime-seconds 3600 --run-id lake-smoke-01
# After checking the smoke results and cleanup report:
./bench ec2 launch --image-name extensions \
  --config configs/graviton-ordered-ducklake.json --run-id ordered-lake-01
```

The smoke workload keeps the 1M dimension, six predicates and four variants but
uses 1,048,576 fact rows, two repetitions, and 32,768 rows per file. S3 staging
requires the EC2 host; use `smoke-extensions.json` for a local HTTP run. To run
the local byte-accounting integration test with a CLI that loads the pinned
extensions, set `JPB_DUCKLAKE_TEST_BINARY` and run
`venv/bin/python -m unittest discover -s tests -p test_ordered_ducklake.py -v`.

### AWS execution

`configs/aws.json` selects profile `join-pruning`, Frankfurt (`eu-central-1`),
On-Demand `m9gd.2xlarge` (8 vCPUs, 32 GiB), and a 24-hour maximum lifetime.
For smoke tests, `--instance-type m9gd.xlarge` uses 4 vCPUs and 16 GiB; the full
configuration deliberately fails preflight on that smaller host.

The laptop needs AWS CLI v2 with an authenticated profile, Docker, and Python
3.12+. The host launcher uses the standard library and AWS CLI; it does not
require boto3 or Terraform. AWS credentials remain on the laptop. EC2 uses its
own instance role and continues operating after the laptop disconnects.
Bootstrap installs the official ARM64 AWS CLI release pinned by version and
SHA-256 in `configs/aws.json`; it does not rely on an Ubuntu `awscli` apt package.
See the [AWS installer documentation](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html).

```bash
# Read-only checks: identity, regional quota/usage, instance offerings, memory,
# disk estimates, Canonical ARM64 AMI, and current On-Demand compute pricing.
./bench ec2 doctor --instance-type m9gd.xlarge --config configs/smoke.json

# Create the dedicated shared infrastructure and publish the built image.
./bench ec2 deploy --instance-type m9gd.xlarge
./bench build
./bench ec2 publish --image join-pruning-suite:local

# The first run uses the smoke configuration and a shorter one-hour budget.
./bench ec2 launch --instance-type m9gd.xlarge --config configs/smoke.json \
  --max-runtime-seconds 3600 --run-id ec2-smoke-01
./bench ec2 status --run-id ec2-smoke-01
./bench ec2 fetch --run-id ec2-smoke-01

# Full runs retain the 24-hour default; launch does not automatically repeat.
./bench ec2 launch --config configs/graviton-full.json --run-id graviton-01

# Optional DuckLake/HTTP image uses its own alias.
./bench build --target extensions --image join-pruning-suite:extensions
./bench ec2 publish --image join-pruning-suite:extensions --name extensions
./bench ec2 launch --image-name extensions --instance-type m9gd.xlarge \
  --config configs/smoke-extensions.json --run-id ec2-http-01

# Exercise data preparation and queries with only 128 MiB of DuckDB memory.
./bench ec2 launch --instance-type m9gd.xlarge --config configs/smoke-spill.json \
  --max-runtime-seconds 3600 --run-id ec2-spill-01
```

Global overrides go before the subcommand, for example
`./bench ec2 --profile my-profile --region eu-central-1 doctor`.
Use `--aws-config path.json` there for a separate stack/environment. The shared
stack provisions one public subnet with no inbound security-group rules,
Systems Manager access, ECR, a private encrypted/versioned S3 bucket, an EC2
instance role, a scoped operator role, and an independent Lambda watchdog.
There is no NAT gateway. The instance uses a public IPv4 address for outbound
downloads; public IPv4, EBS, S3, ECR, logs and transfer costs are additional to
the compute estimate printed by preflight. Stopped EBS and retained artifacts
continue to incur storage charges.

`deploy` uses the configured identity to administer CloudFormation/IAM.
Routine publish/launch/status/fetch/stop/cleanup commands use the stack's
operator role with temporary credentials, kept in memory, when authenticated as
an IAM identity. That identity needs permission to assume the role. AWS does not
allow root sessions to assume roles; a root-authenticated profile operates
directly and prints that fact. Use an IAM identity for routine authentication. No profile files
are changed by the launcher. The operator role intentionally cannot administer
the shared stack. `launch` verifies EC2/PassRole permissions with a dry run.

Each instance has an encrypted 40-GiB root EBS volume and an encrypted 40-GiB
results EBS volume, configurable in `configs/aws.json`. Its local NVMe holds
datasets and spill. Bootstrap verifies the disk models and existing filesystem
signatures before formatting an empty disk, and rejects ambiguous device layouts.
The AMI ID, image digest/config ID, host-worker bundle hash, config, instance type,
deadline and attempt ID accompany the results. A resumed run retains the original
AMI, image, configuration, instance type and container mount paths.

**Deadlines and failure handling.** The lifetime starts at the launch request,
including boot, downloads and image pulling. The suite stops measurement at
23 h 45 min by default and finalizes partial results in the remaining time. For
shorter runs the finalization reserve is scaled, with a minimum of four minutes.
The host shutdown timer and the AWS watchdog start stopping at 23 h 58 min,
leaving margin for AWS scheduling and shutdown latency. The watchdog checks
tagged instances every minute and retries stopping overdue instances; cloud
control-plane outages cannot provide a mathematical wall-clock guarantee.
The watchdog is installed before launch and health-checked before allocating
compute, including protection against bootstrap failure and laptop disconnection.
The 24-hour default applies to each explicitly launched/resumed attempt.

For an explicitly authorized extension on the same running VM,
`infra/aws/extend_running.py` performs a handoff at a completed-query checkpoint.
An operator first extends that instance's `BenchStopAt` tag and installs this helper
alongside `infra/aws/local_resume.py`; the helper extends the Linux shutdown timer,
verifies and uploads the checkpoint, and restarts only the runner with the new
measurement deadline. The VM, pinned image, configuration, and attempt remain the
same. Prepared files are checksum-verified and reused; existing S3 objects are
reused only after their inventory and stored SHA-256 checksums match preparation
and upload records. Extension evidence is included in subsequent checkpoints.
This requires an active query-checkpoint run with its prepared data still present;
changing the EC2 tag alone does not update the runner's in-memory deadline.

Changed artifacts are uploaded as incremental snapshots between measurements, with the runner paused
during checkpoint creation/transfer. Large uploads do not compete with SQL or
microbenchmark timings. S3 validates the supplied SHA-256, and `latest.json` is
published only after the corresponding archive is accepted. Fetch/resume verify
each archive in the snapshot chain and every reconstructed file. Final delivery
uses one complete archive and refreshes its internal `SHA256SUMS`. A final delivery
marker records delivery separately from experiment success: a partial or failed
experiment can be successfully delivered. Upload failure preserves EBS and never
extends the shutdown deadline. Logs and individual completed units are retained.
Analysis/export are retried by the host even after an interrupted worker.
Checkpoint archives currently use a single S3 upload and must be smaller than
5 GiB compressed. Datasets are excluded from these archives. An oversized archive
fails delivery and leaves the EBS copy intact for recovery.

With `suite.checkpoint_microbenchmarks=true`, primitive benchmarks checkpoint
each cluster count and JPB checkpoints each query case, retaining all repetitions
per case. Input/build seeds and JPB filter order remain unchanged. Primitive
cluster cases run in ascending order in separate processes; JPB regenerates
probes per case. This execution protocol is recorded in the manifests and should
not be mixed with old whole-process timing runs. An individual query/case or
dataset preparation still must fit within one attempt's measurement window;
reduce/batch the configuration if it does not. The CLI never silently lowers
scale factors or changes requested repetitions.

```bash
# Stop immediately, retaining EBS; latest uploaded results remain available.
./bench ec2 stop --run-id graviton-01

# After it is stopped, restore verified checkpoints to a NEW instance.
# Missing NVMe inputs are regenerated. Completed measurements are skipped.
./bench ec2 resume --run-id graviton-01

# Fetch refuses to overwrite an existing local run directory.
./bench ec2 fetch --run-id graviton-01 --results out/retrieved

# Terminate stopped run instances; retain their EBS volumes by default.
./bench ec2 cleanup --run-id graviton-01

# Also delete tagged run volumes, only after final delivery has been verified.
./bench ec2 cleanup --run-id graviton-01 --delete-volumes
```

Resume is explicit, does not relaunch a completed experiment, and rejects active
instances/concurrent writers using a conditional S3 lease. A failed bootstrap
with no checkpoint can be resumed from its saved definition. Every attempt has
its own launch record and host/session metadata. `fetch` verifies the archive
SHA-256 and rejects unsafe archive paths and links before extraction. Extracted
results can be analyzed using the same local analysis command described above.

Run cleanup retains S3 results, ECR images and shared infrastructure. To remove
the shared stack after all instances are terminated, use CloudFormation's stack
deletion; the bucket and ECR repository have `Retain` policies and remain for
explicit archival/deletion. Recreating a deleted shared stack with those same
retained names requires resource import or a new stack name. For a bootstrap
failure before any S3 checkpoint, inspect the stopped instance's retained root
volume (`/var/log/cloud-init-output.log` and `/var/log/join-pruning.log`) or the
EC2 console output. No final-delivery marker means EBS must be recovered before
deleting its volumes.
