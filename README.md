# Prefix Range Filter Experiments

Usage:

```bash
python3 run_benchmarks.py --config example_experiment.json
python3 analyze_results.py --experiment-root out/experiments/example-local-validation
```

Everything generated by a run is written under `out/`.

- `run_benchmarks.py`: supported benchmark entry point
- `analyze_results.py`: post-run analysis and chart generation
- `benchmarking/`: runner, workload preparation, and analysis code
- `external_benchmarks/`: benchmark definitions, queries, and workload-specific helpers
- `paper/`: paper configs and figure scripts
- `duckdb/`: DuckDB/Prefix Range Filter prototype

## Paper Filter Microbenchmarks

The main paper config also runs DuckDB's `filter_benchmark` and `range_benchmark`
from the same build as `duckdb-paper`. Activate the project's Python environment
with the packages in `requirements.txt`, then run:

```bash
python3 paper/run_paper_experiments.py --config paper/configs/local_paper_experiments.json
```

The optional top-level `microbenchmarks` object selects `system_name`, shared
`domain_size`, `total_keys`, `min_clusters`, `max_clusters`, `repetitions`, `seed`,
`grafite_bpk`, `diva_bpk`, and `max_fpr`, plus `probe_count` for points and
`queries_per_cluster_count` for ranges. Cluster bounds must be powers of two.
`aggregate` accepts `median` or `mean`. Each executable runs its filters internally;
SQL variants and SQL thread settings do not multiply or configure these measurements.

The publication config requires Bloom, Grafite, Diva, and both PRF modes. Diva
requires Linux x86-64; Grafite requires x86-64. Missing required filters fail the
run before measurements. This smaller config runs on the local platform and
records unavailable competitors:

```bash
python3 paper/run_paper_experiments.py --config paper/configs/local_paper_microbenchmarks_smoke.json
```

To rerun just these measurements or regenerate all figures from saved data:

```bash
python3 paper/run_paper_experiments.py --config paper/configs/local_paper_experiments.json --only-microbenchmarks
python3 paper/run_paper_experiments.py --config paper/configs/local_paper_experiments.json --skip-benchmarks
```

`--only-microbenchmarks` replaces the microbenchmark artifacts while preserving
SQL results, profiles, workload data, and the SQL summary, even when
`overwrite_output` is true. Changes to the saved SQL configuration require a new
experiment name. `--skip-benchmarks` needs neither a build nor benchmark execution;
it validates the saved manifest and CSV checksums. `run_benchmarks.py` also supports
`--only-microbenchmarks`, without figure generation. Binary systems must provide
both tools beside the selected CLI or in its `tools/` directory.

Under `out/experiments/<experiment>/`, the run writes:

- `microbenchmarks/filter-probes/{point,range}.csv`: raw measurements, including
  repetitions, seeds, measured FPR/counts, and range query kinds.
- `microbenchmarks/filter-probes/{point,range}.log` and `manifest.json`: commands,
  status, parameters, available filters, executable checksums, source/build and
  host metadata, and validation results. Failed/incomplete runs cannot be plotted.
- `paper/figures/filter_benchmark_overview.pdf`: point throughput, **range
  throughput**, summary size, build time, and point FPR, in that order.
- `paper/filter_benchmark_series.csv` and `paper/filter_benchmark_summary.{json,md}`:
  aggregated measurements, sample counts, and summaries, also registered in
  `paper/summary.{json,md}`.

The range comparison uses `range_query_kind: "empty"`, which all range-capable
filters measure. PRF's full and mixed ranges remain separate in the artifacts;
Bloom has no range curve. FPR comes directly from measured CSV values. Legacy
point exports with `actual_fpr` still work with `paper/figures/filter_benchmark.py
--csv ... --range-csv ...`; missing negative counts remain unknown. The standalone
range-latency script also selects empty ranges explicitly.

Focused pipeline checks:

```bash
python3 -m unittest discover -s tests -p test_microbenchmarks.py
```

## Generated Join-Pruning Sweeps

New `cross_product` workloads use one explicit sweep and a set of fixed
parameters. Compatible sweeps can also select an explicit query suite:

```json
{
  "kind": "cross_product",
  "params": {
    "fixed": {
      "fact_rows": 100000000,
      "dimension_cardinality": 1000000,
      "key_domain_size": "dimension_cardinality",
      "selectivity": 0.01,
      "join_count": 1,
      "build_key_multiplicity": 1,
      "probe_layout": "uniform",
      "row_group_size": 122880,
      "seed": 7
    },
    "sweep": {
      "kind": "dimension_cardinality",
      "values": [100000, 10000000]
    },
    "query_types": [
      {"kind": "range", "probe_layouts": ["ordered", "uniform"]},
      {"kind": "shoulder", "probe_layouts": ["ordered", "uniform"]},
      {"kind": "seasonal", "cluster_count": 10, "probe_layouts": ["ordered", "uniform"]},
      {"kind": "scattered", "probe_layouts": ["ordered", "uniform"]}
    ]
  }
}
```

Supported sweeps are `dimension_cardinality`, `selectivity`,
`key_domain_size`, `build_key_multiplicity`, `join_count`, `cluster_count`,
and `row_group_size`. A cluster-count sweep defines its query layout and does
not accept `query_types`; cluster counts start at two. Join-count sweeps use
distinct dimension keys and independent uniform fact keys. Multiplicity
sweeps keep total dimension cardinality fixed. The default density mode draws
fact keys only from keys present in the dimension. Row-group sweeps create native
DuckDB fact databases, leaving dimension storage fixed.

`key_domain_size` accepts an integer, `"dimension_cardinality"`, or
`"dimension_distinct_keys"`. The last form is useful for multiplicity sweeps:
it keeps the domain dense while the fixed number of dimension rows is divided
among progressively fewer distinct keys.

Every new-style prepared workload materializes its contract in `definition.json`, its
resolved sweep points in `cases.json`, and per-query parameters in
`queries/query_catalog.json`. These files are the authoritative experiment
description; filenames are only human-readable labels. Legacy cross-product
configurations remain accepted for existing experiments.

The six paper parameter sweeps live in
`paper/configs/local_paper_sweeps.json`. They produce a shared 2x3 runtime
figure with one panel each for join count, build-key multiplicity,
selectivity, density, cluster count, and row-group size:

```bash
python3 paper/run_paper_experiments.py \
  --config paper/configs/local_paper_sweeps.json
```

The standardized sweep writes to `out/experiments/paper-sweeps-standardized-local`
and refuses to overwrite an existing run. Its common baseline is 500 million fact
rows, 100 million dimension rows and key-domain size, 1% selected keys, one join,
one row per key, uniform probes, 122,880 rows per group, and seed 7. All variants
disable `compressed_materialization`; the run uses eight threads and ten repeats.
The one-join, one-row-per-key, 1% selectivity, 100-million density-domain, and
default-row-group points share the same logical keys, payloads, and FK mapping.
The two-cluster point has the shoulder selection. Physical table widths and
storage layouts can still differ between sweeps.

For multiplicity, both the 100-million total dimension rows and whole key domain
stay fixed. Scattered keys spread over the domain as their count decreases.
Shoulder keys form two contiguous ranges anchored at the domain boundaries;
their widths shrink with multiplicity. Separate dimension layouts and fact FK
columns prevent the shoulder layout from changing scattered key spacing.

The density sweep uses `"cardinality_mode": "fixed_selected_build_and_probe"`.
It fixes the **selected** build side at one million unique keys while varying
the domain through 5M, 10M, 30M, 100M, 300M, and 1B. The unfiltered dimension has
one row per domain key, so its predicate selectivity is `1M / domain size`.
Each domain and query shape has its own fact FK column. Every fact row retains
its matching/nonmatching status from the 100M baseline; it samples uniformly
within the corresponding selected set or complement. Consequently, output
cardinality stays exactly constant across domains **within each query shape**.
The number is the realized baseline count (approximately five million), not a
newly rounded target. Away from 100M these probes are conditionally uniform,
not uniform over the whole numeric domain. At 100M the original FK values are
reused exactly. This mode currently requires one join, unique build keys,
shoulder/scattered uniform queries, and default native DuckDB row groups.

Density fact generation uses consecutive batches of 983,040 rows (eight native
row groups), bounding the ASOF lookup and order-restoration sorts. It preserves
the FK values, matching rows, and physical fact-row order. The density workload's
`params.preparation` config sets `batch_rows`, `threads`, `memory_limit`,
`max_temp_directory_size`, and optionally `temp_directory` (absolute or relative
to the workload artifact directory). Batch size must be a positive multiple of
122,880. The paper config uses four preparation threads, 8 GiB memory, and a
64 GiB spill limit; benchmark execution still uses eight threads. These limits
apply to density preparation, including dimension generation.

To continue a run that failed during preparation, keep its output directory and run:

```bash
python3 paper/run_paper_experiments.py \
  --config paper/configs/local_paper_sweeps.json \
  --resume-preparation
```

This reuses completed workload manifests and density dimensions, including
dimensions saved by the earlier generator before its fact-table creation failed.
Fact batches and their restart position commit together, so later failures resume
from the last committed batch. Incomplete workloads other than density restart
their preparation. Resume requires the saved experiment configuration to match;
preparation resources and `overwrite_output` may change. It is only supported
before benchmarking has started. After preparation finishes, benchmarking and
figure generation proceed normally.

`query_catalog.json` distinguishes dimension predicate selectivity, probe
selectivity, selected build cardinality, key density, reference domain, and
expected output cardinality. Figure summaries retain these parameters for each
point. For the density panel, the caption should state: “One million selected
unique build keys; matching fact rows fixed to the 100M-domain baseline per query
shape; conditional uniform FK distribution.” For multiplicity: “100M total
dimension rows and whole key domain; contiguous boundary shoulders or scattered
keys with increasing spacing.” Existing results use their original contracts
and should not be mixed with the standardized run.

The paper configuration also includes the local `dynamic-predicate-transfer/`
checkout as the `rpt-plus` system. Its three variants select `rpt_filter=none`,
`cascade`, and `prf`; the PRF variant explicitly enables
`rpt_prf_scan_pushdown`. The RPT+ system currently runs the Join Pruning, JOB,
TPC-H Skew, and SSB Ordered workloads. String joins and DuckLake are excluded.

The vendored regular PRF is the reference implementation. RPT+/PRF uses its fixed
bitmap sizing, source-statistics multiplicity estimate, 0.1% false-positive
budget, at-most-four direct ranges, and 16 KiB compression cache target. It also
uses the same sector Bloom construction as the fallback when the initial PRF
estimate exceeds the budget. Both engines' JSON profiles expose representation,
FPR, fallback choice, and compression time. RPT+ additionally reports build rows,
estimated multiplicity/distinct keys, shifts, and transfer direction. The two engines still
differ in version, propagation direction, scheduling, and probe batch handling.
Their source distinct-count estimates can differ when they materialize data
separately. The parity check tests compression with identical supplied statistics
and executes SQL against a single shared database, including its persisted
statistics. The SQL fixtures mix selected and rejected rows to avoid RPT's early
selectivity-sampling cutoff.
Source identity is intentionally omitted from experiment metadata.

Focused validation (without generating or running the paper sweep):

The parity script compiles a small fixture against each built library using `c++`
(or `--cxx`) and runs both explicit-statistics and SQL checks at one and four threads.

```bash
python3 -m unittest discover -s tests -p test_cross_product_sweeps.py
dynamic-predicate-transfer/build/paper-native-release/test/unittest '[rpt_prf]'
python3 paper/validate_prf_parity.py --prf duckdb/build/paper-native-release/duckdb \
  --rpt dynamic-predicate-transfer/build/paper-native-release/duckdb
```

## Filter Build Profiling

Standard JSON profiling records comparable elapsed timings in each hash join's
`join_filter` object. The benchmark imports them into `profile_runs` and reports
them for compressed PRF, uncompressed PRF, Bloom-only, and disabled-filter variants:

| Result field (milliseconds) | DuckDB profile field (seconds) | Meaning |
|---|---|---|
| `join_finalize_build_ms` | `join_finalize_build_elapsed_seconds` | Hash-table finalization and filter construction, excluding PRF postprocessing |
| `prf_analysis_ms` | `prf_analysis_elapsed_seconds` | Standalone PRF analysis, including the uncompressed fallback decision |
| `prf_compression_ms` | `prf_compression_elapsed_seconds` | PRF compression, including its bitmap analysis |
| `join_finalize_ms` | `join_finalize_elapsed_seconds` | Total of the three phases above |

The build column is labeled **Join/filter build** because it includes hash-table
work. It is not an isolated PRF or Bloom construction cost. A PRF followed by Bloom
fallback counts as one elapsed build interval; `prf_build_count` and
`bloom_build_count` both increase. Bloom-only runs have zero PRF analysis and
compression; uncompressed PRF can have nonzero analysis but zero compression.
Finalization, perfect-hash, and external-finalization counts are retained too.

`paper/run_paper_experiments.py` and `paper/figures/build_all.py` write
`paper/filter_phases.csv` for every query and variant, including all sweep points.
The paper summary table has separate build, analysis, and compression columns;
JPB runtime figures annotate the three phases. `analyze_results.py` includes
per-query `filter_phases` in each workload/system's `analysis/summary.json` entry.
Existing result databases acquire the new columns when metrics are imported.

These timings come from one separate profiled execution, while runtime bars use
repetition medians. Spans from concurrent joins can overlap and must not be
interpreted as an additive decomposition of query latency. External joins report
initial finalization only. Worker timings are not substituted for elapsed time.
Old `prefix_range_filter.build_phase_elapsed_seconds` and
`compression_phase_elapsed_seconds` have different boundaries; older profiles,
including RPT+ profiles without `join_filter`, therefore show blank CSV cells or
dashes for the new timings. Explicit zero remains zero. Missing phases cannot be
recovered from old timings; a fresh profile is needed.

The profiling pipeline selects `profiling_mode='standard'`, which provides these
elapsed metrics without detailed worker/probe instrumentation. Focused parser,
reporting, migration, and small engine checks can be run with:

```bash
python3 -m unittest discover -s tests -p test_filter_profiles.py
```

Git systems may set `checkout_dir` to use a source tree other than the shared
`duckdb/` checkout. Systems may set `workload_names` to run only a subset of the
configured workloads. Paper figure generation combines systems when
`--system-name` is omitted, so variant labels must be unique across those
systems.

## External Benchmark Dependencies

This shared repository does not include the external benchmark data or prebuilt DuckDB snapshots. It only includes the benchmark definitions, SQL, and helper scripts. Before running the paper config, prepare the missing inputs below.

### JOB

Path: `external_benchmarks/join-order-benchmark`

- No local dataset snapshot is required up front.
- The workload is initialized from `schema.sql` and `load.sql`.
- During preparation, the benchmark downloads the source data referenced by the load script.
- To materialize a reusable local DuckDB snapshot instead of re-running initialization each time:

```bash
python3 external_benchmarks/join-order-benchmark/materialize_local_db.py
```

### String Joins

Expected file: `external_benchmarks/string-joins/airports.csv`

- Download the `airports.csv` file from the OurAirports dataset.
- Place it at the path above, or point `airport_csv_path` at a different local copy in your config.

### TPC-H Skew

Expected file: `external_benchmarks/tpch-skew/tpch_sf100_z2.duckdb`

- Generate the skewed TPC-H data with the generator from the data-induced predicates paper.
- Load the generated tables into a DuckDB database file.
- Store that database at the path above, or update `external_benchmarks/tpch-skew/source.json` to point at your local file.

### SSB Ordered

Expected file: `external_benchmarks/ssb-ordered/ssb_sf100.duckdb`

- Generate the SSB data with the SSB data generator.
- Load the tables into DuckDB.
- Reorder the `lineorder` table by `lo_orderdate` before saving the benchmark database.
- Store the resulting DuckDB file at the path above, or update `external_benchmarks/ssb-ordered/source.json`.
