# Join-Pruning Benchmark

This repository is organized around two steps:

```bash
python3 run_benchmarks.py --config example_experiment.json
python3 analyze_results.py --experiment-root out/experiments/example-local-validation
```

The config file defines:

- which workloads to generate or prepare
- which DuckDB systems to benchmark
- which SQL variants to run on each system
- benchmark settings such as repetitions, thread count, and profiling

Everything generated by a run is written under `out/`, which is ignored by git.

## Repository Layout

```text
run_benchmarks.py
analyze_results.py
benchmarking/
  experiment_config.py
  experiment_runner.py
  duckdb_build.py
  duckdb_runner.py
  results_analysis.py
  svg_charts.py
  manifests.py
  query_inventory.py
  workloads/
external_benchmarks/
example_experiment.json
example_remote_http_experiment.json
out/
```

- `run_benchmarks.py`: the only supported CLI entry point
- `analyze_results.py`: post-run comparison and visualization entry point
- `benchmarking/`: internal implementation modules
- `external_benchmarks/`: checked-in benchmark definitions and queries
- `example_experiment.json`: a small end-to-end example config
- `example_remote_http_experiment.json`: the same suite with remote-HTTP Parquet external workloads
- `out/`: generated workloads, SQL, system builds, results, and summaries

## Config Shape

The top-level JSON has four sections:

```json
{
  "experiment_name": "example-local-validation",
  "output_root": "out/experiments",
  "overwrite_output": true,
  "workloads": [],
  "systems": [],
  "benchmark": {}
}
```

### Workloads

Supported workload kinds:

- `single_join_clusters`
- `cross_product`
- `external`

Example:

```json
{
  "name": "tiny-ranges",
  "kind": "single_join_clusters",
  "params": {
    "build_size": 32,
    "domain_multiplier": 4,
    "fact_rows": 200,
    "cluster_counts": [2, 4, 8],
    "dummy_string_cols": 1,
    "dummy_string_len": 8,
    "seed": 7
  }
}
```

For external workloads:

```json
{
  "name": "job",
  "kind": "external",
  "source_dir": "external_benchmarks/join-order-benchmark"
}
```

An external workload directory must contain `queries/` and may optionally provide `source.json`.

Supported external preparation modes:

- `init_sql_paths`: initialize a fresh benchmark database by running SQL files with `prepare_duckdb_binary`
- `database_path`: reuse or copy an already prepared DuckDB database file
- `remote_http_parquet`: export all base tables to Parquet, serve them over local HTTP, and add a fixed latency to each HTTP request

Example SQL-initialized external benchmark:

```json
{
  "benchmark_name": "join-order-benchmark",
  "queries_dir": "queries",
  "metadata_path": null,
  "init_sql_paths": ["schema.sql", "load.sql"]
}
```

Example prebuilt-database external benchmark:

```json
{
  "benchmark_name": "tpch-skew",
  "queries_dir": "queries",
  "metadata_path": null,
  "database_path": "tpch_sf100_z2.duckdb",
  "database_handling": "reuse"
}
```

`database_handling` is optional when `database_path` is set:

- `reuse`: run queries against the checked-in database in place
- `copy`: copy the database to `out/.../workloads/<name>/benchmark.duckdb` before benchmarking

Remote-HTTP Parquet mode is enabled in `source.json` and currently only requires one parameter:

```json
{
  "benchmark_name": "join-order-benchmark-remote-http",
  "queries_dir": "../join-order-benchmark/queries",
  "init_sql_paths": [
    "../join-order-benchmark/schema.sql",
    "../join-order-benchmark/load.sql"
  ],
  "remote_http_parquet": {
    "latency_ms": 25
  }
}
```

When this mode is enabled, preparation exports every base table into Parquet files under `out/.../workloads/<name>/remote_parquet/`.
Benchmark execution then starts a local HTTP server with byte-range support, adds the configured fixed latency to each request,
and creates temporary views over `read_parquet([...])` so the benchmark queries themselves do not need to change.

## Systems

Supported system kinds:

- `binary`: benchmark an existing DuckDB CLI binary
- `git`: clone a DuckDB repository, check out a ref, build it, and benchmark that binary

Example binary system:

```json
{
  "name": "local-duckdb",
  "kind": "binary",
  "binary_path": "/opt/homebrew/bin/duckdb",
  "variants": [
    {
      "label": "default",
      "setup_sql": []
    },
    {
      "label": "no_compressed_materialization",
      "setup_sql": [
        "SET disabled_optimizers='compressed_materialization';"
      ]
    }
  ]
}
```

Example git-built system:

```json
{
  "name": "duckdb-main",
  "kind": "git",
  "repo": "https://github.com/duckdb/duckdb.git",
  "ref": "main",
  "variants": [
    {
      "label": "default",
      "setup_sql": []
    }
  ]
}
```

## Benchmark Settings

Example:

```json
{
  "benchmark": {
    "repetitions": 5,
    "threads": 8,
    "prepare_duckdb_binary": "duckdb",
    "collect_profiles": true
  }
}
```

- `repetitions`: measured executions per query and variant
- `threads`: optional `SET threads = ...`
- `prepare_duckdb_binary`: DuckDB CLI used to initialize SQL-backed external workloads
- `collect_profiles`: collect one profiled run per query and variant for `cumulative_rows_scanned`

## Artifact Layout

A run named `prefix-range-study` writes to:

```text
out/experiments/prefix-range-study/
  config.json
  analysis/
    summary.json
    comparisons/
    charts/
  workloads/
    <workload-name>/
      queries/
      manifest.json
  systems/
    <system-name>/
      checkout/
  sql/
  profiles/
  results.duckdb
  summary.json
```

For generated workloads and SQL-backed external workloads, the workload artifact directory also contains
`benchmark.duckdb`. For external workloads with `database_handling: "reuse"`, the manifest points at the
source database path instead of materializing a copy under `out/`.

The repository source tree stays clean because generated artifacts live under `out/`.

## Analysis

After a run finishes, analyze it with:

```bash
python3 analyze_results.py --experiment-root out/experiments/example-local-validation
```

The analyzer:

- reads `results.duckdb`
- backfills missing profiling runs when older experiments only contain timing data
- writes per-query comparison JSON files under `analysis/comparisons/`
- writes one SVG chart per workload under `analysis/charts/`

Visualization behavior by workload kind:

- `single_join_clusters`: line charts over cluster count for runtime and cumulative rows scanned
- `cross_product`: bar-chart panels for runtime and cumulative rows scanned
- `external`: bar-chart panels for runtime and cumulative rows scanned

## Running The Example

The checked-in example uses small generated workloads and a local DuckDB binary:

```bash
python3 run_benchmarks.py --config example_experiment.json
```

That run creates:

- generated benchmark databases and query files
- generated SQL workloads per system and variant

To run the same suite with the two checked-in external workloads served as remote Parquet over HTTP with fixed per-request latency:

```bash
python3 run_benchmarks.py --config example_remote_http_experiment.json
```
- a results database at `out/experiments/example-local-validation/results.duckdb`
- a summary file at `out/experiments/example-local-validation/summary.json`
- profile JSON files under `out/experiments/example-local-validation/profiles/`

Then analyze the run:

```bash
python3 analyze_results.py --experiment-root out/experiments/example-local-validation
```

That creates:

- `out/experiments/example-local-validation/analysis/summary.json`
- per-workload comparison JSON files
- per-workload SVG charts

## Notes

- The join-order benchmark under `external_benchmarks/join-order-benchmark` loads data from remote parquet files during initialization.
- The TPC-H skew benchmark under `external_benchmarks/tpch-skew` is wired as a prebuilt DuckDB database and uses `database_handling: "reuse"` to avoid copying the 35 GB file into `out/`.
- For offline validation, use generated workloads such as the example config.
